# Protected credit identities: Step 9B.8.1

The separate [Step 9B.8.2 evidence views](protected-credit-evidence.md) extend account inspection with explicitly chosen statement, dated-current-report and entry reads. Those views preserve native unselected evidence; the metadata contract described here remains distinct from financial selection, acquisition and payment status.

The protected **Credit Cards** section opens saved HDFC billing-account identities, explicitly inspects an account, and shows the separate directory of saved credit source handles and their retained link decisions. It uses the four [credit identity and provenance reads](credit-identity-reads.md). No financial values, imports, provider access, account mutations, statement allocation or physical-card membership are added.

## Acceptance contract recorded before implementation

- Validate every row and exact response shape before rendering. Accept only safe HDFC/INR billing identities, canonical nonzero application references, bounded positive revisions, safe nicknames and explicit lifecycle states. Reject additional private fields and inconsistent source links.
- Load only the first account page on entry. Account inspection is explicit and rechecks the selected identity and minimum revision. Archived accounts remain inspectable. An empty directory is not a zero-balance or debt-free claim.
- Keep the source directory independent of account selection. Never-linked and explicitly unlinked sources remain distinct; mapped sources may target another or archived billing account. A source handle does not establish acquisition, statement completeness or live connectivity.
- Bind history to the selected source and preserve the clicked mapping target while separately retaining the highest mapping revision observed in this view. Require consecutive descending revisions, exact predecessors and explicit reasons/targets; preserve the clicked revision's immutable target when it appears. Newer decisions may appear. Target account lifecycle is observed when read, separately from the historical mapping decision.
- Retain one bounded data page and only bounded directory cursor metadata. Refresh and back navigation read fresh data. Clear prior data while loading or after failure, and ignore late responses after navigation or session loss.
- Use compact Indigo & Apricot light/dark layouts, keyboard focus, 44px controls and explicit loading, empty, unavailable and historical states. No browser persistence, URL identifiers, prototype fallback or amounts.

## Interaction and meaning

**Billing accounts** loads 25 identities at a time, in application-reference order. Each account shows a safe label, HDFC issuer, INR billing currency and observed active/archived state. **Inspect account** reads the identity again before showing its revision and expandable reference. A billing account is distinct from a physical card. There are no card numbers, last-four digits, limits, outstanding values, due amounts or payment claims in this increment.

**Source directory** lists **Saved sources** across the owner’s credit accounts. It includes handles that have never been linked, explicitly unlinked handles with a retained revision, and links to active or archived accounts. It is not a filtered list of one account's imports. The expandable references identify application records, not bank-supplied card references. **Inspect linked account** reads the target identity explicitly.

**Link history** reads one source's immutable decisions, newest first. It shows the revision, reason, predecessor and historical target, with that target's currently observed lifecycle. The first page must not regress below the highest mapping revision already observed in this history view. Refreshing, paging to earlier decisions and returning to the newest page preserve that bound separately from the original clicked source binding. Once a mapping has been observed, the same view cannot return to an empty never-linked history. Continued pages must start at the immediately preceding revision and reach revision one or provide an exact bounded continuation; missing history cannot appear as successful exhaustion. Earlier targets can be inspected through a fresh account read. The source handle and link decision do not prove an imported statement or the current financial state of an account.

Pages contain at most 25 rows. The directory retains at most 100 cursor positions and displays a limit notice when further navigation is bounded. There is no automatic page traversal or total-count inference. History retains only its current page, original clicked source binding, scalar continuation and highest observed revision. Native INR billing currency remains unchanged by the display-currency preference. No monetary values or financial chart geometry are present to mask.

## Security and failure behavior

All four reads use the existing active MFA session, same-origin cookie request, signed CSRF, workspace-context binding, response size/deadline limits and no-store policy. Response parsing occurs inside the protected authentication controller. Malformed, extra-field, foreign-identity, regressed-history and inconsistent mapping responses block the workspace before any partial page renders. Expected data-unavailable/conflict/limited failures clear previous account/source/history context and offer a fresh account-directory reload.

Navigation unmounts the section and invalidates pending view results. Sign-out, lock, expiry and session replacement retain the existing authentication generation/abort boundary. No records, source references, card digits or credentials enter browser storage, URLs or telemetry. There are no credentials or file inputs and no backend route, dependency, schema, privilege or recovery-format changes.

## Verification

A subsequent response-consistency hardening preserves the highest source-link revision observed in the current history view, separately from the original clicked mapping. It rejects a refreshed newest page below that floor or an empty newest page after a mapping has been observed. Refreshing the current page, paging earlier and returning to the newest page retain that floor. This is defensive response consistency, not evidence of a database concurrency defect. The two new UI cases cover newer-head and formerly unlinked-history regression; existing validator assertions also cover null and below-clicked floors. The existing layout and read endpoints are unchanged.

The subsequent history-floor correction passed all 71 metadata cases as part of a 171-case two-suite run in 27.68 seconds; the other 100 cases cover a separate financial-evidence increment. Earlier combined attempts retained one keyboard-fixture failure with 170 passes, then 24 failures with 147 passes after a test-label encoding error. The corrected run passed without relaxing validation or deadlines. These are targeted results; the complete integrated gate is recorded separately.

The original focused suite passed all 69 credit identity projection/UI cases in 15.96 seconds after the wording refinement. They cover strict response fields, canonical identities, source state distinctions, exact selected bindings, revision floors and consecutive history, directory/history paging, initial StrictMode/busy loading, failure clearing, late navigation/lock/session replies, sign-out and keyboard/accessibility semantics in both themes. The initial combined run passed all 187 cases across six existing account, banking, authentication, context, preference and workspace suites; its new 68-case suite had 29 failures because the new UUID pattern omitted one four-character group. Correcting the pattern and adding the malformed-short-UUID regression produced the passing 69-case rerun. No timeout, validation boundary or existing test was relaxed.
