# Credit-card value contracts

Step 9B.1 defines pure, frozen Python values before owned credit-account persistence. It extends neither the existing asset event/snapshot schema nor any HTTP/import contract. These are application normalization requirements, not facts about an HDFC export layout.

## Acceptance boundary

- An INR billing statement retains its billing-period start/end, statement date, optional due date, opening and closing liability, total due and minimum due separately. Missing monetary fields use `FinancialValue` with an explicit missing reason; supplied zero stays zero. A missing due date remains unknown. Only the billing period must be ordered; no equality or chronological relationship between statement/due/transaction/posting dates is invented.
- Liability balances, source total due and unbilled evidence are signed: positive means owed; negative means a credit in the owner's favor. Known credit limits and minimum due amounts are nonnegative normalization magnitudes. Minimum due is not required to equal or be derived from total due. Available credit can be negative or exceed the limit; it is never derived from outstanding or treated as cash.
- Separately dated current evidence has its own required source date and optional precise instant, plus independent reported outstanding, unbilled, limit and available-credit values. If supplied, the instant's original local date must match the source date; UTC conversion must not replace that local date. This evidence is not added to a statement checkpoint or used to calculate remaining payment.
- Each entry supplies an explicit posted-debit, posted-credit, pending-debit, pending-credit or unresolved role and an explicit movement/ambiguous/unsupported treatment. Billing amounts are nonnegative INR magnitudes or explicitly missing; the role supplies the liability direction. Transaction and posting dates may be missing independently. Pending roles cannot claim a posting date. Unresolved roles cannot claim supported movement treatment.
- An optional original amount is separate INR/USD cash-kind evidence with the same nonnegative magnitude convention. Its source representation and currency remain intact. No exchange rate, conversion, fee difference or equality with billed INR is inferred. This slice does not store raw issuer sign labels or narration; a future verified normalizer must preserve minimized source evidence separately and explicitly resolve sign conventions before producing these values.
- Reconciliation accepts an immutable tuple of at most 1,000 entries and an explicit complete/partial/unknown coverage claim. The claim comes from the caller; matching arithmetic does not prove completeness. No identifiers, de-duplication, overlap/history guarantees or account association are implied. Legitimate repeated equal entries are counted separately.
- A complete claim with known opening/closing liabilities and supported posted entries with known amounts and posting dates inside the billing period permits exact opening + debits - credits arithmetic. Pending entries are excluded. An explicitly complete empty tuple can compare opening and closing; a partial/unknown empty tuple cannot establish zero movement.
- Reconciliation distinguishes matched, mismatched and unavailable. Missing fields, partial/unknown coverage, unresolved/ambiguous/unsupported entries, missing posting dates or out-of-period posted entries produce explicit unavailability. Out-of-period posted entries are not silently filtered. A mismatch retains the exact calculated closing and source-closing-minus-calculated difference without adjustments. An arithmetic result outside the existing financial bounds is unavailable.
- All amounts reuse bounded `FinancialValue` cash precision; dates/instants reuse `FinancialDate` and `FinancialInstant`. Runtime type checks reject floats, booleans, arbitrary iterables, wrong value kinds/currencies and coerced dates. Frozen/slotted contracts, private representations and fixed error descriptions prevent supplied values from appearing in diagnostics. Arithmetic must be independent of ambient decimal precision, rounding and traps.

## Exclusions and next dependency

There is no paid/overdue status, remaining-to-pay calculation, income/spending classification, bank matching, repayment schedule, interest forecast, utilization or net-worth inference. No card number, last four digits, account/source identity, raw narration, credentials, upload, parser, provider access, dependency, API, migration or persistence is introduced.

Step 9B.2 adds only an owned HDFC/INR billing-account registry with safe nicknames and archival. Physical-card identity, source mappings and durable statement/liability evidence remain later increments with owner isolation, immutable history and encrypted recovery. See the [credit-card plan](credit-cards-plan.md), [financial persistence plan](financial-data-plan.md) and [security requirements](security.md).

## Implementation and verification

The [pure contract module](../backend/trading_api/credit_cards.py) exposes `CardStatementValues`, `CardCurrentValues`, `CardEntryValues`, `CardReconciliation` and `reconcile_card_statement`. Values are not serialized to storage or wired into the application. Reconciliation uses the existing exact `sum_cash` arithmetic and exposes only a fixed unavailability reason when a result exceeds its magnitude bound.

The [synthetic contract tests](../backend/tests/test_credit_cards.py), run together with the existing financial primitive suite, pass 243 cases. They cover matched and mismatched statements, overpayments, missing versus zero, independently missing due fields, explicit coverage including empty and repeated entries, pending exclusions, ambiguous/unsupported treatment, posting-date boundaries, original currency separation, source-local timestamp precision, hostile decimal context, arithmetic magnitude limits, bounded collections, strict runtime types, frozen private representations and invalid result states. Focused Ruff checks and module type checking pass. No database, network, schema or application behavior is exercised by this slice.
