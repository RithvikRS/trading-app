# Credit statement checkpoint evidence: Step 9B.4

This increment adds only internal, unselected statement observations over owned credit source mappings. It does not establish a verified HDFC layout, import coverage, a chosen account balance or financial posting. Current outstanding/limit evidence, activity entries, reconciliation, payment status, source acquisition, public routes and screens remain separate.

## Acceptance contract recorded before implementation

- Two tables retain an immutable observation interpretation and its required statement child. The observation binds owner, internal root UUID, revision/predecessor, source handle, exact mapping revision, billing account, fixed statement kind/contract version, fixed initial/correction reason and server timestamp. Root source, account and kind cannot change. No raw report, digest, filename, narration, issuer reference, physical-card identity, card digits or arbitrary metadata is accepted.
- Internal callers allocate a root UUID server-side before calling record and retain it for explicit retries. A request with expected revision n targets n+1. An exact existing target revision returns that retained revision even after a later correction, only after rechecking current owner, mapping and active account. Changed current mapping, an archived account or conflicting retained fields reject the write/retry. Retained history remains separately readable. Equality includes original decimal spelling and frozen mapping revision. New roots never merge because dates or amounts match.
- Statement values preserve period start/end, statement date, optional due date, opening/closing liability, total due and minimum due. Dates are finite and in years 0001–9999; only the period is ordered. INR cash retains original decimal strings, exact bounded numeric values and explicit missing reasons; zero remains supplied zero. Only minimum due is nonnegative. There are no inferred date/amount equalities.
- Revalidate every nested frozen date/value object and its cached fields. Reject tampering, floats, booleans, wrong kinds/currencies and malformed/missing values privately before SQL; never silently repair an invalid supplied object.
- Composite owner foreign keys bind the exact mapping and account. A same-root predecessor key preserves source/account/kind and contiguous history. Reciprocal deferred parent/child keys require exactly one statement child at commit, including bootstrap restore. Structural constraints apply to every role; runtime admission is a separate boundary. UPDATE/DELETE and timestamp/identity rewrites are unavailable.
- Runtime writes use the shared credit owner advisory lock, READ COMMITTED, fresh owner/context checks after waits, current mapping checks and an active-account row lock held through commit. Both parent and child INSERT boundaries check admission. A deactivation during a tested lock wait rejects the operation; this does not claim a global owner-deactivation/commit ordering contract.
- At most 1,000 observation revisions per owner, including history. Read pages default to 25 and cap at 100; root pages use UUID keysets and history uses descending revisions. Latest means latest revision of one root, never selected/current account liability. Archived records remain historical evidence for an active owner; unknown and foreign identifiers are indistinguishable.
- Failed inserts, deferred completeness failures, interruption and outer rollback leave no partial observation. Two concurrent corrections have one winner; exact same requests return the same retained revision. Archive-first rejects evidence; evidence-first can finish before archival and remains readable afterward.
- Two-owner tests cover direct SQL grants/constraints, inactive/context loss, exact source/mapping/account binding, unsupported isolation, quotas, actual lock-wait/deactivation ordering, revision races and private diagnostics.
- Migration/recovery tests cover fresh/repeated/failed upgrade, empty downgrade/re-upgrade, populated downgrade denial and separate-cluster recovery of exact missing/zero/corrected evidence across remapping/archive. Old sessions and live connector state stay excluded.

## Internal implementation

The [statement service](../backend/trading_db/credit_statements.py) exposes server-side root allocation and transaction-scoped record, get, list and history operations. A returned record remains part of its caller's transaction until that context commits. Exact retries can return an earlier retained revision; they do not declare it the current account balance.

[Unit cases](../backend/tests/test_credit_statements.py), [PostgreSQL cases](../backend/database_tests/test_credit_statements.py) and [migration cases](../backend/database_tests/test_credit_statement_migration.py) exercise the acceptance boundary below the public application routes.

## Migration and recovery boundary

Migration 0021 follows the 0020 source mapping prerequisite. Two new tables produce 48 application tables, 44 durable tables and the same four omitted live session/admission/connector tables. Recovery format 17 includes every column and the complete reconstruction order; deferred parent/child references permit complete restoration but reject an incomplete object. Existing 4 MB plaintext and 1,000-row-per-table global recovery bounds remain. No new identifier key or investment completion-baseline change is introduced.
