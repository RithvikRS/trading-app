# Step 3C: Local PostgreSQL and migrations

The database foundation runs only on the development computer or a disposable CI runner. Security takes priority: separate credentials, restricted roles, explicit migrations, and guarded test cleanup are established before storing application records. The default API mode serves liveness without a database connection; opt-in browser authentication uses the restricted registry described below. [Step 3D](ownership-isolation.md) extends this baseline with owner tables and row-level security. [Step 3E.1](authentication-foundation.md) adds the identity-lookup role. [Step 3E.2](browser-sessions.md) adds the private session/security registry. Financial data remains a later increment.

## Runtime and compatibility

The service uses the official PostgreSQL **17.11 bookworm** image, pinned by its multi-platform SHA-256 digest in `infra/postgres/compose.yaml`. PostgreSQL 17 is a supported Supabase upgrade target. No extensions beyond PostgreSQL's default `plpgsql` are required. The selected hosted project's exact version, extensions, TLS, roles, and grants must still be verified before deployment; a local PostgreSQL container does not reproduce Supabase's managed environment. [Supabase upgrades](https://supabase.com/docs/guides/platform/upgrading), [official PostgreSQL image](https://hub.docker.com/_/postgres).

SQLAlchemy 2.1.6, Alembic 1.20.1, and Psycopg 3.3.6 with its binary distribution are pinned in `backend/pyproject.toml` and `uv.lock`. The binary driver includes its client libraries; dependency updates must account for those as well as Python packages. The current release supports Python 3.14. [SQLAlchemy releases](https://www.sqlalchemy.org/download.html), [Psycopg installation](https://www.psycopg.org/psycopg3/docs/basic/install.html).

Use a running local Docker Engine 28 or newer with Linux containers and Docker Compose. Windows uses Docker Desktop's Linux engine. Remote Docker contexts and endpoint overrides are rejected. Engine 28 is the minimum because older engines have documented limitations around loopback port isolation. The tested development versions are Engine 29.6.1 and Compose 5.3.0. [Docker port publishing](https://docs.docker.com/engine/network/port-publishing/).

## Commands and lifecycle

After the [Python setup](development.md#local-python-api), run from the repository root:

```powershell
python scripts/database.py up
python scripts/database.py migrate
python scripts/database.py status
python scripts/checks.py database
python scripts/database.py down
```

| Command | Effect |
| --- | --- |
| `up` | Generate private local credentials once, start PostgreSQL, and provision the local roles and migration metadata schema; does not run application migrations |
| `migrate` | Upgrade to the committed Alembic head with the migrator identity in one transaction |
| `status` | Check server identity and print only the current schema revision |
| `checks.py database` | Start a fresh independent test cluster, run destructive migration/permission tests, then stop and remove its temporary files |
| `down` | Stop/remove the development container and network; retain its named volume and credentials |

Development uses project `trading-development`, database `trading_dev`, and `127.0.0.1:55432`. Its named volume is `trading-development_development-data`. Repeating `up` preserves data and reapplies the bootstrap grants with the existing credentials. Repeating `migrate` at the current head is a no-op. No automatic migrations run during API startup, and the browser has no database connection.

Each test run uses a random `trading-test-<random>` project, database `trading_test`, fresh passwords, a dynamically assigned IPv4 loopback port, and a 256 MiB tmpfs data directory. Guarded fixtures checkpoint before schema rebuilds so completed-test WAL can be recycled without relaxing durability or raising storage limits. It cannot mount the development volume. Test cleanup validates the URL's driver, literal host, database, user, port, and absence of query overrides before connecting. Explicit driver addresses also prevent libpq environment/service settings from redirecting a validated loopback target. It then checks PostgreSQL's database name, major version, and unique cluster marker before destructive SQL; the administrator connection repeats that check. Cleanup rejects an unexpected project name. Failed Docker cleanup is a failed check and retains the local credential directory for recovery.

## Credentials and privilege boundaries

Four independent 256-bit random passwords live in ignored `.cache/postgres/development/` files. Test credentials live under `.cache/postgres/tests/` only for that run. Unix directories/files use 0700/0600; Windows disables directory inheritance and grants the current user and SYSTEM access. Only the bootstrap file is mounted into PostgreSQL through a Compose file secret. Passwords are not command arguments, committed environment values, Docker configuration environment values, or printed connection strings. The official entry point reads the file into the container process environment during initialization; Docker administrators and the local account remain trusted.

These local files are not a production secret store, and Compose secrets do not encrypt their host files. Protect the development computer and its disk. Never put personal records into these services. Do not delete the credential directory while retaining its database volume: replacement passwords cannot authenticate to the existing cluster.

| Identity | Granted responsibilities | Important restrictions |
| --- | --- | --- |
| `trading_bootstrap` | Local cluster administrator and database owner; provisions roles/grants | Used only by the explicit local provisioning tool and disposable fixtures; never passed to the API |
| `trading_migrator` | Owns `app_meta`, migration metadata, and application schema; can create schema objects | Not a superuser; cannot create roles/databases, replicate, or bypass RLS |
| `trading_auth` | Resolve active identity mappings and mark initial MFA completed | No workspace data, provisioning, identity changes, MFA reset, DDL, or role escalation |
| `trading_runtime` | Connect to its application database and use the `app` schema | Owns no schema/table; no DDL, temporary tables, role membership/escalation, migration-table access, or implicit table/function grants |

PUBLIC loses database connection/temporary privileges and access to `public`. Future migrator-created tables, sequences, functions, and types do not grant PUBLIC access. Runtime table privileges are added explicitly with the [owner policies](ownership-isolation.md). Search paths use `pg_catalog`; migration SQL qualifies application objects. Step 3C establishes role separation; Step 3D adds the per-owner row policies. [PostgreSQL privileges](https://www.postgresql.org/docs/17/ddl-priv.html).

Host and Unix-socket authentication use SCRAM-SHA-256, including bootstrap initialization. Data checksums are enabled. The dedicated bridge publishes only loopback and disables communication between peer containers; it is not an outbound traffic firewall. The container has no Docker socket or host networking. It has a 512 MiB memory limit, one CPU, 100-process limit, bounded logs, and no privilege escalation. PostgreSQL has 30 connections and 64 MiB shared buffers. These are local development limits, not measured Oracle capacity.

SQLAlchemy uses at most two pooled connections with no overflow, a five-second checkout/connect/lock limit, and 15-second statement/idle-transaction limits. Migrations use unpooled connections. SQL echo is off and parameters are hidden. CLI failures omit driver exceptions, SQL, credentials, and tracebacks; database statement and parameter logging are disabled. These settings reduce disclosure but do not turn local database logs into safe public artifacts.

## Migration and recovery contract

Bootstrap creates only `app_meta`, owned by the migrator, for Alembic's version table. Revision `0001_private_schema` creates the empty `app` schema and grants runtime schema usage. That baseline revision adds no tables beyond migration metadata. Revision `0002_workspace_ownership` adds owner/identity mapping and non-financial preferences. Revision `0003_auth_identity_lookup` adds restricted identity lookup and the MFA marker. Revision `0004_browser_sessions` adds private session, revocation, admission, and security-event tables. Revision `0005_preference_revisions` adds versioned display preferences. Revision `0006_accounts_sources` adds four [account/source tables](accounts-source-mappings.md). Revision `0007_instruments` adds six [instrument/position identity tables](instrument-identities.md). Revision `0008_import_staging` adds five [evidence/staging/review tables](import-staging.md), retaining forced owner policies and narrow grants. Revision `0009_financial_events` adds four [event/component/movement tables](financial-events.md), explicit staged posting state and versioned batch digests without inventing historical posting evidence. Revision `0010_lots_corrections` adds three [lot tables and retained correction histories](lot-evidence-corrections.md) with normalization contract 3. Revision `0011_snapshots` adds three [snapshot/selection tables](snapshot-evidence.md), source timestamp precision and legacy-compatible normalization contract 4. Revision `0012_market_evidence` adds two [market observation/selection tables](market-evidence.md) with exact prices, NAVs and directed FX evidence. Revision `0013_event_evidence` adds two [provider identity/evidence tables](event-evidence.md). Revision `0014_statement_boundaries` adds [statement date basis and checkpoint boundary metadata](statement-boundaries.md), preserving all four earlier normalization contracts. Revision `0015_completion_baseline` adds [bounded completion state tokens](completion-preflight.md) and common insert serialization for remaining identity/staging roots. Revision `0016_completion_receipts` adds [atomic limited-coverage receipts](completion-receipts.md) and immutable row dispositions. Revision `0017_reconciled_completion` adds [full source-period comparisons](reconciled-completion.md) with immutable native scopes and exact input sets. Revision `0018_indmoney_authorization` adds [encrypted connector custody, pending callbacks and audit events](indmoney-authorization.md), with financial runtime access denied and live credentials excluded from recovery. Revision `0019_credit_billing_accounts` adds the separate [HDFC/INR billing-account identity registry](credit-account-identity.md), with forced owner RLS, immutable identity, bounded `READ COMMITTED` runtime writes and revision-checked archival. That increment adds no balances, physical-card/source mappings or routes. Revision `0020_credit_source_mappings` adds [opaque credit source handles and immutable mapping history](credit-source-mappings.md), retaining forced owner RLS, narrow grants, bounded admission and active-target checks. That increment adds no external identifiers, physical-card membership, financial values or routes. Revision `0021_credit_statement_evidence` adds [immutable credit statement observations and required checkpoint children](credit-statement-evidence.md). Composite mapping/predecessor keys preserve ownership and historical binding; reciprocal deferred references reject incomplete pairs during runtime writes and restore. Strict dates and exact INR values, bounded admission, current write authorization and immutable history apply without selecting an account liability or adding provider acquisition, movements or routes. The current head, `0022_credit_current_evidence`, adds [separately dated current credit evidence](credit-current-evidence.md). Fixed child kinds and null-safe stored discriminators extend reciprocal deferred keys to require exactly one matching statement or current child, including restore. Existing statement inserts retain their defaults; root source/account/kind and the shared quota remain fixed. Original source-local instants, independent exact INR values, `READ COMMITTED` admission and fresh owner checks after waits add no selection, liability movement, provider acquisition or public route. The local migration metadata schema is separate from any Supabase-managed schema.

The migration runner verifies the target and role attributes, takes a transaction-scoped advisory lock shared with bootstrap, and supplies that transaction to Alembic. Both schema changes and the revision record roll back if a revision fails, including a failed initial upgrade. Concurrent migrators wait only up to the lock timeout. There is no automatic stamp, table creation, or retry that can conceal a partial migration. [Alembic connection sharing](https://alembic.sqlalchemy.org/en/latest/cookbook.html#connection-sharing).

Downgrades and alternative migration directories are accepted only against a verified disposable test cluster. The baseline downgrade uses `DROP SCHEMA` without `CASCADE`; unexpected objects stop it. Normal development recovery uses a corrected forward migration. Existing applied revisions should not be edited after shared use. [Step 3G](local-packaging.md#encrypted-foundation-recovery) adds an encrypted foundation-record restore drill on disposable clusters. Development/hosted backups and deployed rollback procedures remain later operations work. [Step 4E.1](snapshot-evidence.md#migration-and-recovery) makes disposable downgrade guards inspect exclusively locked tables with schema-owner visibility, restoring forced policies before commit; failures roll back those changes.

If a command fails, check that Docker is running on a local Linux context, port 55432 is free, and all four credential files still exist. Upgrading from Step 3D adds only the new auth file and preserves the original three. `docker ps --filter label=com.docker.compose.project=trading-development` shows container state without credentials. Do not paste Docker inspection environments, database logs, or password files into issues. If a disposable run is interrupted, identify its exact `trading-test-<random>` project using Docker's Compose labels and its matching ignored directory before stopping it. Never remove the development volume as part of test cleanup. There is deliberately no development reset command.

## Verification and remaining scope

The shared [verification runner](verification.md) adds a **Database checks** job using the same fresh-cluster procedure locally and in CI. Tests cover clean/repeated upgrades, downgrade/re-upgrade, initial and subsequent migration failure rollback, unexpected-object downgrade refusal, SCRAM and wrong-password rejection, restricted runtime privileges even when test-only DML grants exist, closed future object grants, server-marker mismatch, concurrent migration lock timeouts, failed-cleanup credential retention, libpq address overrides, and rejected unsafe targets before network access. Source policy checks reject public ports, unpinned images, trusted authentication, privileged containers, and persistent test storage.

Local Windows evidence on 23 October 2026: development startup, repeated migration/status, and 25 real PostgreSQL tests passed. The backend suite has 71 passing tests; Ruff, strict mypy, and the Python dependency audit passed. This records the Step 3C baseline evidence. Later ownership/RLS validation is documented in [Step 3D](ownership-isolation.md). Hosted Supabase authentication/database behavior, backup restore, and Oracle resource behavior remain unverified. Local authentication integration is covered separately in [Step 3E.1](authentication-foundation.md).

[Step 3F.2](display-preferences.md) adds migration `0005_preference_revisions`. It preserves existing display values, introduces a database-maintained revision, and keeps the existing role/RLS boundaries. Apply it before starting the updated authenticated workspace. Disposable tests cover preserved values, repeated application, downgrade/re-upgrade, and atomic rollback of a failed upgrade.
