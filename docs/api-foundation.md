# Step 3A: Local Python API scaffold

The API in `backend/` is a local development foundation. Supabase Auth on Free with FastAPI is the [selected authentication direction](authentication-options.md); authentication is not implemented yet. The frontend still runs independently with fictional data. The API scaffold itself creates no database, provider connection, user account, cloud resource, or deployment. Later [verification](verification.md) and [local database](database-foundation.md) tools run independently.

## Runtime and dependencies

Python 3.14.9 is pinned in `.python-version`; the project accepts the 3.14 bugfix line from that patch onward. uv 0.13.5 is pinned as the dependency tool. Direct versions and the full dependency graph are recorded in `pyproject.toml` and `uv.lock`. uv rejects source builds, so dependencies must have compatible published wheels. This is an application run as a module, not an installed distribution; packaging arrives in 3G.

Python 3.14 remains in bugfix support and avoids introducing the newly released 3.15 line while database/authentication integrations are still to come. Patch/dependency updates require refreshing the pins and checks; a lockfile does not remove the need for maintenance. [Python releases](https://www.python.org/downloads/), [uv projects](https://docs.astral.sh/uv/guides/projects/).

## HTTP contract

| Request | Result |
| --- | --- |
| `GET /api/v1/health/live` | `200`, exactly `{"status":"ok"}` |
| Unknown route, including docs/schema/login/financial routes | `404`, generic error and server-generated request ID |
| Unsupported method on liveness | `405`, generic error; `Allow: GET` |
| Request validation error | `422`, without supplied inputs or validation details |
| Unhandled application error | `500`, without exception details or traceback |
| Untrusted Host header | `400`, without reflecting the supplied hostname |

Liveness reports only that this process can answer HTTP. It proves nothing about database, authentication, provider availability, or deployment readiness. No readiness endpoint exists. It returns no version, environment, dependency list, system path, credentials, or account information.

The application disables OpenAPI/interactive documentation, automatic slash redirects, debug output, and CORS. HTTP responses passing through the application boundary receive `Cache-Control: no-store`, `nosniff`, a deny-by-default content policy, frame denial, no-referrer, and a newly generated request ID. Client-provided request IDs are ignored. A response interrupted after headers are sent is terminated rather than reported as a completed request.

Protocol errors and concurrency rejections generated by Uvicorn occur before the application boundary and may not carry its JSON envelope or headers. They contain no application data. Future proxy/TLS and resource controls must cover these paths too.

## Configuration and local entry point

Run `python -m trading_api` through the locked environment using the [development commands](development.md#local-python-api). Only the following application environment variables are accepted:

| Variable | Default | Accepted values |
| --- | --- | --- |
| `TRADING_API_ENVIRONMENT` | `development` | `development` or `test` |
| `TRADING_API_PORT` | `8000` | ASCII integer from 1024 through 65535, without whitespace or leading zeroes |

An unknown `TRADING_API_` setting, misspelling, invalid value, or unsupported command-line argument stops startup with exit code 2 and a generic `configuration_invalid` event. Supplied values are never printed. `.env.example` is reference material; the application does not discover or load `.env` files. There are no credentials to supply at this stage.

The entry point fixes binding to `127.0.0.1`, one process, no reload, no forwarded-header trust, no access log, no server-identification header, and no WebSocket protocol. It uses h11 with a 16 KiB incomplete-event limit, 32 concurrent connections/tasks, backlog 64, and five-second keep-alive/graceful-shutdown bounds. These are conservative development defaults, not measurements of Oracle capacity or substitutes for later request-size/rate controls. [Uvicorn settings](https://uvicorn.dev/settings/).

Only `localhost` and `127.0.0.1` are trusted Host names. Hosted environment names and application bind/debug/auth-bypass/CORS overrides are rejected. Directly launching another ASGI server can bypass the entry-point settings; use the documented command. Container/public binding, trusted proxies, TLS, cookies, database roles, and hosted configuration arrive with their respective features. Loopback does not protect against a compromised local computer.

## Logging boundary

Application and server logs use a structured allowlist: level, fixed event name, generated request ID, and bounded numeric status. Raw log messages, formatting arguments, exception text, tracebacks, request targets, query strings, headers, bodies, and client addresses are omitted. Unrecognized server messages become `server_event`. Access logging is disabled, including for unknown routes.

This deliberately limits diagnostic detail while there are no protected operational tools. Future integrations must preserve this contract and add safe, meaningful event codes instead of printing provider payloads or exceptions. No external exporter or telemetry service is configured.

## Verification and limits

Tests exercise configuration rejection, absence of implicit dotenv loading, local startup restrictions, route/method/Host behavior, security headers, generated request IDs, generic validation/server errors, and interrupted responses. Fault routes exist only in tests. A subprocess test starts the documented entry point on a temporary loopback port, sends real HTTP and malformed protocol input, and checks that synthetic sensitive markers do not appear in process logs.

Local evidence includes clean locked installation, lint/format/type checks, the backend suite, and an advisory lookup of installed dependency versions. These do not prove hosted compatibility or security of future authentication/database features. This API-only evidence does not cover Supabase, PostgreSQL, Oracle, or real data. Later database evidence is recorded separately in [Step 3C](database-foundation.md). Frontend behavior is unchanged and remains independent.

Verification on 23 October 2026 with Windows and Python 3.14.9: 48 backend tests passed; Ruff lint/format and strict mypy checks passed; a fresh runtime-only locked environment successfully created the application. pip-audit 2.10.1 reported no known vulnerabilities in the installed backend dependencies. The real-socket test requires local loopback access; a network-restricted runner cannot supply that evidence. Frontend checks were not repeated because its source, dependencies, and configuration did not change.
