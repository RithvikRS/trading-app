# Frozen native comparison inspection: Step 7B.4.1

A saved reconciled [completion receipt](saved-receipt-inspection.md) now opens its native comparison scopes and the source/combined equations retained at completion. This interface uses the existing [receipt comparison reads](completion-receipt-reads.md). It introduces no provider access, financial mutation, activity completion, input-row inspection, backend route or schema change.

## Scope and financial meaning

Select **Inspect native comparisons** on a reconciled receipt, then choose one comparison. Limited receipts have no comparison entry. The scope list preserves the whole batch, including other accounts and positions; the holding that opened the receipt does not filter the list. Each request uses 25 rows in ascending opaque identity order, not date order. Cash currencies and position units remain separate.

Each scope shows its native currency or units, original period and explicit date basis. Opaque receipt, account, position and comparison identities, the rule version and retained input count are in expandable source details. Select one scope to see the **Source report** and **Combined saved evidence** sides independently. Both retain opening, posted movement, closing, calculated closing, difference, posted count and pending count. Pending activity is excluded from the posted total. Different source/combined activity counts are valid.

**Balanced at completion** describes the frozen comparison under its saved rule. Later corrections, source mappings, selections or quotes do not replace these inputs. No current balance, lifetime history, tax basis, return, FX conversion or cross-scope total is inferred. INR/USD preference changes do not convert native evidence. [Step 7B.4.2](frozen-input-inspection.md) now exposes the retained opening, activity and closing rows for either side. Each selection preserves exact native evidence and original lineage; returning to this view refetches the frozen equation.

## Exact validation and privacy

[Comparison projections](../frontend/workspace/src/comparison-evidence.ts) bind each scope to the selected receipt and bind an inspection to every immutable field of its scope. Exact fields, nonzero opaque identities, valid periods, native cash/unit shape, date basis, rule version and bounded counts are mandatory. Equation inspection also requires the matching reconciled receipt: source posted plus pending entries and two distinct checkpoints must fit within its row count, even when the period starts and ends on the same date. Combined history can exceed that batch row count because it may contain previously saved events. Scope pages retain only cumulative counts for traversal checks; full traversal must match the receipt's saved scope count. Refresh uses the count preceding the current page and restarting clears it. Earlier scope pages and financial payloads are replaced.

Opening and closing strings retain the existing 32-character source limit and magnitude below 1e18. Derived comparison values have at most 36 characters and magnitude below 1e22. Cash has at most two fractional digits; units have at most twelve, with nonnegative unit checkpoints. Exact scaled integers verify the returned equations, zero difference, common source/combined boundaries and input-count identity without sending financial values through binary floating point. Original decimal lexemes, signs and trailing zeros remain the display values.

[ComparisonInspection](../frontend/workspace/src/ComparisonInspection.tsx) renders a controlled view inside the receipt inspector. Only fixed authenticated POST reads are used: `/receipts/scopes/query` and `/receipts/scopes/inspect`. The existing MFA, origin/CSRF, owner-isolation, session-context, response-size and no-store boundary remains in place. One requested comparison is inspected at a time; the browser does not fetch every frozen input or automatically load all scopes.

Masking removes all amount/quantity strings, including zero differences, from visible and accessible text, attributes and geometry. Loading or failure clears the preceding view. Navigation, session replacement, lock and sign-out discard it; generation and unmount guards ignore late responses. Malformed responses use the existing blocked protocol screen, and unavailable reads show fixed generic errors. No browser storage, private provider reference, automatic retry or synthetic production fallback is added.

## Verification

[Focused regressions](../frontend/src/test/workspace-comparisons.test.tsx) cover native scope and immutable metadata binding, exact high-magnitude/fractional equations, count consistency, source admission limits, complete bounded traversal, refresh/restart, other-account scopes, unavailable reads, strict protocol blocking, keyboard focus, masking and stale-response disposal. Existing receipt, lot, account-activity and investment regressions remain prerequisites, including the lot-history lower bound after returning from a receipt.

After adding the required receipt binding and source-row capacity guard, the affected comparison (86) and receipt (89) suites passed **175 tests**. Eleven new regressions cover exact/over-limit source counts, split posted/pending entries, 98/99 activity rows for a 100-row receipt, distinct checkpoints on a same-day period, unrelated receipt context, larger valid combined history and initial/refreshed rejection clearing. The earlier five-suite run passed 308 tests across comparison, receipt, activity, lot and investment views. TypeScript and both production builds passed again after the guard. Full integration uses the [standard verification groups](verification.md).

Synthetic Chromium checks covered 1440 px and 390 px widths in light and dark modes: native INR/USD and twelve-place unit values, independent source/combined precision, other-account scopes, keyboard focus, collapsed source details, display preference changes without finance requests, masking including zero differences, sign-out clearing, protocol-failure clearing and empty local/session storage. Automated WCAG 2 A/AA and 2.1 A/AA checks, including contrast, found no violations; neither width had horizontal overflow. The eight captures were visually inspected and remain unchanged because the receipt-count guard changes no layout. A focused Chromium probe after the guard verified initial source overflow rejection, refreshed overflow clearing with different old/returned values, and valid combined history larger than the receipt row count followed by sign-out clearing. No live provider or private statement was used.
