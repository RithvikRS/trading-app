# Security requirements

Security is the highest project priority. These requirements cover confidentiality, integrity, and availability of financial data. They are planned controls; completion must be demonstrated before the relevant feature is used with personal data.

The current Overview, Investments, Banking, Budgets, and Connections prototype uses fictional records, loopback-only servers, bundled assets, restrictive browser headers, and display-only preference storage. Searches and screen controls stay in memory; routes use allowlisted screen names and opaque fixture IDs without financial values or account/folio details. Unknown or malformed detail routes show an unavailable screen. Masking hides amounts, units, quotes, lot purchases/fees, bank balances/movements, reconciliation differences, and activity values in the DOM and accessible attributes. Transaction inspection also suppresses raw narration/reference, since source text can contain amounts. Banking source records are immutable fixtures. Transfer and category decisions share an in-memory undo history, separate from original records. Category previews list eligible changes and exclusions before applying; source availability, ownership, direction, role, prior classification, and pair membership are revalidated. Stale previews fail as a whole, and bulk selection clears when filters change. Pending records, investment funding, refunds, and retained transfer pairs cannot be directly recategorized. Verified refunds follow their purchase category and remain unresolved when evidence is incomplete or excessive. Matching checks known sample account ownership, posting state, equal native amounts/currency, source roles, and the three-day calendar window. Confirmation revalidates availability and exclusive pair membership. These client-side fixture checks are not authentication or production authorization. Pair and category previews, structured references, spending/refund/coverage values, and announcements follow shared privacy rules. See its [implemented boundaries and limitations](ui-prototype.md#security-boundary). Authentication, database policies, and production hosting protections remain future work; [Step 3B](verification.md) adds repository secret detection and CI; no real data belongs in the prototype.

Monthly budgets use the same immutable source records and review classifications. Limits are scoped to the known sample owner/month, parsed as bounded exact INR values, and stored only in memory with separate undo history. Masking also removes budget drafts, accessible monetary values, and progress geometry from the DOM; hidden editors cannot save or remove limits. Budget statuses distinguish incomplete coverage from known zero. Recurring expectations do not enter budget actuals or remaining amounts. No authentication, database, connection, or deployment capability is added.

Cash-flow history uses the same immutable ledger and review model. Only known owner/account records contribute, with explicit period selectors and supplied coverage intervals. Reconciliation includes every eligible posted record in exactly one role; paired transfers and refunds validate against the full source evidence before account/date filtering. Comparisons are withheld unless both matching-day windows have complete source and classification coverage. Missing history is not filled with zero. Month/account/day/category selections and source/table disclosures stay in memory, and only allowlisted transaction IDs enter routes. Masking removes chart geometry, axes, monetary table content, ratios, and accessible values. Historical source inspection uses its own statement period. No new dependencies, external requests, credential handling, persistence, backend, or deployment are introduced.

Recurring suggestions are allowlisted fixture definitions bound to full original source identity, including payee, narrative, account, owner, date, amount, currency, status, and category. Confirmation revalidates distinct monthly expense occurrences, exclusive source membership, and current classifications; stale evidence fails. Changed or missing evidence retains the decision as Needs review and excludes expectations. Ambiguous store payments cannot be confirmed. Pending sources never establish recurrence or count as paid. Date arithmetic clamps monthly schedules without using the machine clock. Expected values use exact INR units, with variable ranges excluded from fixed totals, and never mutate the ledger, balances, budgets, or cash flow. Decisions, evidence keys, selections, and undo history stay in memory; only opaque source IDs enter existing inspector URLs. Masking removes ranges, individual amounts, and totals from rendered/accessibility content. No payment execution, notification, scheduler, file input, network integration, or production authentication is introduced.

[Connections](ui-prototype.md#connections-and-source-coverage-step-2e1) derives source coverage from existing financial fixtures and keeps simulation state in a separate model. Only two known INDmoney IDs accept allowlisted scenarios/actions; statement examples never receive invented authorization. Expired/revoked examples require explicit simulated renewal; rate limits require advancing the supplied retry window. Attempts cannot overlap for a source, complete after cancellation, or silently advance receipt/financial dates. Show sample outcome is an explicit local step, with no timer or request. Loading cancels pending attempts, empty/reload clears local scenarios and controls, and connection reset affects only this domain. Fixed dates, a bounded history, and plain-text messages contain no financial values. Search is literal and limited to 80 characters. Only existing display preferences persist. No file/credential entry, network calls, provider access, authentication, durable audit log, or dependency is added.

[Bank sample previews](import-samples.md) now validate explicit dates, bounded exact amounts, source kind, and known owner/account/provider identities. Each source row has one disposition. Immutable-field conflicts and ambiguous overlap never silently overwrite or add candidate amounts; canonical incoming IDs keep identical copies from adding movement twice. Source arithmetic remains separate from the candidate subset, uses native minor units, and excludes pending entries. Missing balances, unreadable amounts, and mixed source currencies stay unavailable. Original text renders as escaped text, including a deliberately hostile fictional string. Masking removes raw source fields, descriptions, matching financial evidence, and search inputs from the DOM; stored preferences contain no financial or review state. Routes allow only fourteen bank/investment batch IDs. Import controls and fixed comparison baselines remain isolated from connection simulations and all financial/review domains. No dependencies, uploads, parsers, file access, or network requests are added.

Bank import review now binds proposed actions to the complete supplied batch/baseline evidence, mapping, current decisions, operation, and session revision. Applying or completing revalidates atomically; stale actions leave decisions/history unchanged. Scoped identities count once, distinct-overlap inclusion requires supplied evidence, and exclusions cannot hide invalid fields, incomplete coverage, missing records, or reconciliation differences. Native minor-unit arithmetic checks the full source separately from retained baseline plus unique candidates. Completion is idempotent within the session and records only a sample receipt; reopening clears it before editing. Import undo/reset remains independent of financial and connection state. Masking dismisses previews, hides receipt details, and disables amount-affecting changes/completion. Nothing enters network requests, URLs, or persistence beyond existing display preferences. These checks are not parser security, durable idempotency, authentication, or production authorization. [Investment walkthroughs](imports-prototype-plan.md#step-2e4-investment-statement-walkthroughs) share this isolated history and revision boundary.

Investment rows validate the known owner/account/instrument and fund scheme/plan/option/form/folio, bounded source IDs, calendar dates, event kinds, and allowed fields for each record type. Units (8 places), quotes (6), and native amounts (2) reject unsupported precision rather than silently rounding. Marked values use the existing exact valuation rounding and a bounded display range. Snapshot identities include the instant; activity and lot identities include source/account/record identity. Conflicting immutable values cannot be overridden by source preference. Independent checkpoints cover supplied and retained identities, opening/activity/closing units and cash, and remaining lot units. Missing cash checkpoints, acquisition history, fees, basis, or required source identities block completion; exclusions cannot repair them. Snapshot-only completion explicitly makes no transaction, lot, tax, or full-account claim. Both source versions remain inspectable; original fixtures stay unchanged.

All investment action previews bind source and baseline evidence, revision, scope, decisions, operation, and the shared session serial. Repeated completion is idempotent; changing evidence hides incompatible receipts. Bank and investment undo/reset restore both parts of the import domain, separately from financial and connection state. Masking removes units, raw strings, source descriptions, pending choices, receipt details, and monetary markup from DOM/accessibility output. Malicious-looking fixture text remains escaped text. These are local consistency/privacy controls only; no production access-control, parser, or audit guarantees are implied.

## Assets and trust boundaries

Protect bank and investment records, statements, identifiers, session tokens, integration credentials, encryption keys, backups, and financial calculation history. A broker token may permit trading even when this app only displays holdings; record the provider's actual permissions.

Trust boundaries include the browser and API, public network and application host, host and Supabase, worker and financial providers, uploaded document and parser, administrator and runtime identities, and primary storage and backups. External statements, connector responses, descriptions, and imported links are untrusted input.

## Threat model

| Threat | Required response | Verification |
| --- | --- | --- |
| Account takeover or stolen session | MFA, protected sessions, rate limits, revocation, and tested recovery | Rejected invalid/expired sessions, renewal and logout tests, recovery exercise |
| Unauthorized record access | Server-side ownership checks and database policies with a restricted runtime role | Cross-account and future cross-user access tests, including pooled connections and jobs |
| Exposed database or credentials | Network restrictions, verified TLS, least privilege, external secret management, and redacted logs | Negative connection tests, role/grant inspection, secret scanning |
| Malicious statement or provider payload | Constrained isolated parsing, validation, safe rendering, and no arbitrary URL fetching | Malformed/oversized file, resource exhaustion, injection, and outbound-access tests |
| Duplicate, forged, or partial imports | Source attribution, idempotency, atomic commits, reconciliation, and reviewed corrections | Reupload, overlap, interrupted-import, and mismatch tests |
| Compromised dependency, build, or server | Locked dependencies, vulnerability review, constrained containers, patching, and restricted CI | Dependency/container review and deployed configuration inspection |
| Deleted data, ransomware, or provider loss | Independent encrypted backups, restricted deletion rights, and tested restoration | Restore into an isolated environment and reconcile records |
| Overpowered broker integration | Prefer provider-enforced read-only scopes and separate execution credentials | Document and verify token capabilities before enabling a connector |

## Implemented API scaffold boundary

[Step 3A](api-foundation.md) adds a local-only Python process with a minimal liveness route. The documented entry point fixes loopback binding, disables proxy trust/access logs/server identification, rejects unsupported application settings and hosted modes, and exposes no debug/OpenAPI/login/data routes. Host checks, no-store/security headers, generic error responses, and allowlisted structured logs are covered by synthetic tests, including a real local subprocess. No external telemetry exporter is configured. These are scaffold controls, not authentication, database isolation, public-hosting protection, or proof of financial-data safety.

[Step 3C](database-foundation.md) establishes local PostgreSQL privilege boundaries: separate bootstrap/migrator/runtime passwords, SCRAM authentication, loopback publication, bounded connections, private application/metadata schemas, and explicit transactional migrations. Disposable tests reject unsafe targets before cleanup and verify DDL/escalation denial and migration rollback against a real server. Credentials stay in restricted ignored local files, and CLI errors omit sensitive driver details. These are synthetic local controls; owner policies/RLS, hosted TLS, production secret custody, and backup recovery remain later work.

## Authentication and sessions

The [foundation plan](foundation-plan.md) defines the required session and ownership contract. [Supabase Auth on Free with FastAPI](authentication-options.md) is selected, with password plus authenticator-app TOTP as the initial factor direction. Authentication endpoints, mandatory-factor enforcement, recovery, and bounded server sessions remain unimplemented until Step 3E. Verify the maintained integration and actual provider entitlement before use. Require MFA for the owner and administrative cloud accounts, disable public registration for the personal version, and review enrollment and recovery as part of authentication. Do not build custom cryptography.

Use short-lived or bounded sessions with server-side revocation and secure, HttpOnly, appropriately SameSite cookies. Protect state-changing requests against CSRF and validate origins. Keep credentials and refresh tokens out of browser local storage, URLs, and frontend bundles. Use exact CORS allowlists, rate limits, generic authentication errors, and documented expiry behavior.

Restrict the personal deployment through a private network or identity-aware gateway as well as application authentication. The gateway is an additional boundary, not a replacement for API authorization. Its product and recovery method remain to be selected.

## Database access

Step 3 proves API and database isolation with two synthetic owners, missing identity, attempted ownership changes, and transaction/connection reuse after success, failure, and cancellation. Direct Python database access must establish trusted transaction-local owner context; Supabase authentication helpers are not assumed to receive a browser identity automatically. Session lookup uses a separate narrowly scoped path before that owner context exists. These controls are planned, not active in the current prototype.

- Permit hosted database access only from explicitly allowed application and administrative network addresses, covering the actual IPv4/IPv6 and pooler routes used.
- Enforce TLS and verify the server certificate and hostname. Connection failures must not trigger an unencrypted fallback.
- Disable unused Supabase REST/GraphQL Data API access and keep financial tables in an unexposed schema. Review grants on new tables, functions, and sequences; do not rely on project defaults.
- Give API and worker roles only necessary operations. They must not be schema owners, superusers, or roles that bypass row-level security. Separate migrations and backup privileges from runtime credentials.
- Enforce ownership in the API and row-level security where applicable. Define how trusted server-authenticated identity reaches database policies; an arbitrary client-supplied owner ID must never authorize access. Test identity cleanup across pooled transactions, failures, and background jobs.
- Treat administrative consoles, service credentials, and migration roles as privileged access. MFA, limited use, and auditability apply to them too.

Reference: [Supabase network restrictions](https://supabase.com/docs/guides/platform/network-restrictions), [TLS enforcement](https://supabase.com/docs/guides/platform/ssl-enforcement), and [Data API security](https://supabase.com/docs/guides/api/securing-your-api).

## Secrets and encryption

Prefer official OAuth or scoped provider authorization. Login and consent should occur at the provider where supported. Bank passwords and broad mailbox access are not default import mechanisms. Document scopes, renewal, expiry, and revocation for every integration. A connector requiring credentials that also permit trading needs a separate documented decision before it is enabled.

Keep integration secrets server-side and encrypt persisted tokens with authenticated encryption from a maintained library. Manage keys outside the database and its backups, using a secret manager or KMS with narrowly scoped workload identity. OCI Vault is a candidate; the exact key custody and recovery design remains to be selected. Record key versions and test rotation and revocation.

Require protected storage for database data, statements, backups, and VM disks. Review swap encryption and crash-dump behavior because decrypted statements and secrets may appear in process memory. Protect decryption keys separately from the encrypted data. Encryption at rest does not prevent an attacker controlling the authorized application from reading data; least privilege, host isolation, and incident response remain necessary.

Never commit live credentials, private statements, PAN/account identifiers, dumps, or decrypted fixtures. Configure ignore rules and secret scanning before introducing any real data or secrets. Development and tests use separate credentials and synthetic or irreversibly sanitized data.

## Statement ingestion and data privacy

Validate type and content instead of trusting filename extensions. Restrict file size, page count, parser time, memory, and concurrency. Parse with a non-root isolated process, no provider credentials, and network access disabled unless a specific reviewed requirement exists. Reject unsupported formats rather than invoking unsafe conversion or macros. Review PDF, archive, and spreadsheet dependencies before accepting those formats.

Store uploads privately with opaque identifiers, authorized downloads, and no public URLs. Retain originals only for a defined reconciliation period or explicit user need. Remove temporary decrypted files after processing and on failure. PDF passwords must not enter logs or persistent storage by default.

Escape imported text in the interface, sanitize any permitted rich content, use a restrictive content security policy, and prevent spreadsheet formula injection in exports. Allowlist connector destinations to avoid server-side request forgery. Do not execute instructions, scripts, or links found in imported content.

Minimize logs and metrics: keep event type, result, timing, and pseudonymous identifiers; redact tokens, document contents, account numbers, and full provider payloads. Define retention for statements, financial records, audit events, and backups, including how deletion propagates and when retained backups expire. Do not send financial data to third-party analytics or external data-processing services without a separately reviewed purpose and explicit authorization.

## Delivery and operations

[Step 3B verification](verification.md) runs locked local/CI checks, strict dependency audits, workflow-policy tests, and Gitleaks over reachable history and the current source snapshot. Tool archives and cached binaries are hash-verified; scanner failures never count as a pass. Workflow jobs use disposable runners, pinned actions, read-only repository permission, no retained Git credentials, no shared dependency caches, and no production secrets or deployment jobs. Secret scanning has explicit source/history and file-format limits and does not establish branch protection.

Pin and lock dependencies, review known vulnerabilities, scan for secrets before commits, and grant CI minimal permissions. Build using synthetic data and keep production secrets out of build output and logs. Use non-root containers, narrow filesystem permissions, resource limits, and minimal exposed ports. Restrict SSH administration and keep OS and dependencies patched.

Audit security-relevant events, import confirmations, permission changes, exports, corrections, and future orders. Use append-only application permissions for audit records and consider independent audit copies before multi-user or trading use. Do not claim that records held on a compromised host are inherently tamper-proof.

Backups, restore exercises, monitoring, and incident handling are specified in [operations](operations.md). Treat backup contents and recovery credentials as production-sensitive data.

## Release gates

The local UI prototype uses fictional data only. Before handling real data, verify authentication, ownership checks, secret handling, private storage, and safe ingestion. Before hosted use, additionally verify:

1. MFA, registration restrictions, session revocation, account recovery, and protected network entry work.
2. Database network restrictions and certificate verification reject unauthorized or invalid connections.
3. Runtime roles and policies prevent unauthorized access; migrations cannot accidentally expose tables.
4. Logs, builds, commits, and error responses contain no secrets or personal records.
5. Import atomicity, deduplication, and reconciliation prevent silent data corruption.
6. Encrypted backups and separately protected keys restore successfully into an isolated environment.
7. Dependencies, server configuration, patching, resource limits, and alerts have been reviewed; known material security failures are resolved.

Record evidence and remaining limitations with the relevant feature or deployment documentation. Passing checks reduces risk; it does not constitute a guarantee of security or a compliance certification. Public multi-user access and real trade execution require expanded threat models and a separate security review before activation.
